# DormBook — PG, Hostel & Dormitory Management (SaaS)

Node.js + Express + SQLite (one file on a persistent disk), vanilla-JS app, JWT sign-in.
Off-site backups and ID-proof copies go to Cloudflare R2. Live updates between phones.

---

## Deploy on Render (recommended)

### 1. Cloudflare R2 (off-site backups) — 5 minutes
1. Cloudflare dashboard → **R2** → **Create bucket** → name it `dormbook-backups` (location: Asia-Pacific).
2. R2 → **Manage R2 API Tokens** → **Create API token** → permission **Object Read & Write**, only this bucket.
3. Copy the **Access Key ID** and **Secret Access Key** (shown once).
4. Your **Account ID** is on the R2 overview page (the part before `.r2.cloudflarestorage.com`).

### 1b. Supabase Storage (second off-site copy) — 3 minutes
1. Supabase dashboard (project `uqwzpodpnegzejhqdtta`) → **Storage** → **New bucket** → `dormbook-backups`, **private**.
2. **Storage → S3 Connection** → **New access key**. Copy the Access Key ID, Secret, and the **Region** shown on that page.
3. In Render set `SUPABASE_S3_ACCESS_KEY_ID`, `SUPABASE_S3_SECRET_ACCESS_KEY`, `SUPABASE_S3_REGION`
   (`SUPABASE_URL` and `SUPABASE_BUCKET` are preset). Every backup and ID file then goes to R2 **and** Supabase;
   if one is down or lost, the other still has everything. The app's database itself stays on the Render disk.
   (Free Supabase projects limit one file to 50 MB — far above a PG's database for a long time.)

### 2. Create the Render service
1. Render → **New** → **Blueprint** → choose this GitHub repo. Render reads `render.yaml`
   (web service, Starter plan, Singapore, **1 GB disk at `/var/data`**, health check).
2. Fill the values it asks for:

| Variable | What to type |
|---|---|
| `AES_256_KEY` | **New install:** `openssl rand -hex 32`. **Moving from Railway:** the SAME value as on Railway |
| `SUPERADMIN_EMAIL` | your email — you sign in to the admin panel with it |
| `SUPERADMIN_PASSWORD` | a strong password (10+ characters) |
| `SUPERADMIN_MOBILE` | your 10-digit mobile (optional) |
| `R2_ACCOUNT_ID` | Cloudflare account id |
| `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` | from step 1 |
| `R2_BUCKET` | `dormbook-backups` |

`JWT_SECRET`, `CRON_SECRET`, `WEBHOOK_SECRET` are generated by Render. `DB_DIR=/var/data` is preset.

3. **Apply**. First build takes ~2 minutes. Open the `https://…onrender.com` address and sign in
   with `SUPERADMIN_EMAIL` / `SUPERADMIN_PASSWORD`.

> ⚠️ Do not use Render's **Free** plan: it has no disk, so every deploy would wipe all data.
> The app refuses to start without a disk at `DB_DIR` (you'll see the reason in the logs).

### 3. Moving existing data from Railway to Render (no data lost)
1. On **Railway**, add the same four `R2_…` variables and redeploy. On start it makes a backup and
   copies it to R2. In the admin panel → **System & Backups** → press **💾 Back up now** and then
   **☁️ Copy all ID files to R2**. Check both show in the R2 list.
2. On **Render**, before the first deploy (or with an empty disk) add `RESTORE_FROM_R2=latest`.
   On start it downloads the newest backup from R2, then opens it. Log line: `[RESTORE] ✅ Restored …`.
3. Use the **same `AES_256_KEY`** as Railway. Sign in and check guests, payments and an ID photo.
4. Remove `RESTORE_FROM_R2` in Render (it never overwrites an existing database, but keep it clean).
5. Android app: change `server.url` in `capacitor.config.json` to the Render address and build
   the APK once (Actions → Build APK). To send people who still open the old address to the new
   one, set `REDIRECT_TO_URL=https://your-app.onrender.com` on Railway.
   Tip: use your own domain (Render → Settings → Custom Domain), so the address never changes again.

## Super-admin panel

Sign in with the super-admin email. Menu:

| Page | What you can do |
|---|---|
| Dashboard | Customers by status, revenue this month / all time, renewals and trials ending this week |
| Customers | Add customer, view (counts only — guests' private data is never shown), record payment, edit plan / dates / notes, extend trial, suspend / lift, reset owner password, delete with all data |
| Users | Every owner and staff login: search, edit name / mobile / email / role, new password, unlock, block / unblock, delete |
| Payments | What PG owners pay you: record (extends their paid period automatically), edit, void (never deleted), printable receipt |
| Plans & Pricing | Add / edit / hide plans (price, days, bed limit). Active plans also show on the sign-up screen |
| Reports | Revenue & sign-ups by month, by mode, by plan, renewals due, top customers, CSV downloads |
| Content & Branding | App name, tagline, **logo**, support phone / WhatsApp / email (shown on sign-in), FAQ (shown in My Account) |
| Super-admins | Add / edit / delete super-admin logins (at least one always stays active) |
| System & Backups | Version, database size and health check, backups on disk and in R2, back up now |
| Admin Log | Every change made in the panel: who, what, when |

**Subscriptions:** when you record a payment, the customer becomes *Active* until the paid period ends.
After that they get `SUBSCRIPTION_GRACE_DAYS` (default 7) more days, then sign-in is blocked with
"Subscription ended. Contact support to renew." Customers activated before this update have no end date
and keep working.

**Locked out of the panel?** Render → Environment: `SUPERADMIN_RESET=true` (with `SUPERADMIN_EMAIL` and
`SUPERADMIN_PASSWORD`), redeploy, sign in, then delete `SUPERADMIN_RESET`.

**OTP is off.** Forgot password → the sign-in screen shows your support contact; you reset it in
Customers → More → Reset owner password (or Users → Password). Staff still get a one-time login code
from their owner (shown on screen, shareable on WhatsApp). To turn SMS / WhatsApp OTP back on later:
`OTP_ENABLED=true` (+ `MSG91_AUTH_KEY`, `MSG91_OTP_TEMPLATE_ID`).

## For PG owners and staff (sign-in to sign-out)
- **Sign up** → 30-day free trial starts → **Today** shows the trial banner and a **Get started** checklist
  (add beds → address & phone → UPI QR → first guest → staff login), each with a one-tap button.
- **Keep me signed in on this device** (on by default in the Android app) keeps people signed in after the
  app is closed; **Sign out** asks once, then clears the device.
- Trial ends or payment is late → sign-in shows the plans and your WhatsApp / phone / email instead of a dead end.
- Show / hide password on sign-in and sign-up. Check-in with no beds sends the owner to bed setup.

## Live updates and app updates
- Every signed-in phone keeps a light live connection. When anyone at the same PG saves something,
  other phones refresh the list / dashboard they are on (forms and open popups are never refreshed
  under your fingers — a "New updates · tap to refresh" bar appears instead).
- After a deploy, open apps notice the new version and reload themselves at a safe moment.
  The Android app loads the live site, so no APK download is needed for updates.

## Safety built in
- Backups: at every start, every night 03:15 IST, and on demand — on the disk (newest 14) and in R2.
- Rate limits on every route (sign-in per IP and per account with back-off, admin changes, exports,
  live connections, public pages) — all numbers configurable in `.env.example`.
- Health check `/api/v1/health` answers 503 if the database cannot be read, so Render restarts it.
- Clean shutdown on deploy (finishes requests, saves the database).
- A database hiccup answers "try again" — it never signs users out.

## Troubleshooting
- **App does not start on Render** → Logs show `[BOOT ERROR]` with the exact setting to fix
  (missing disk, `DB_DIR`, `JWT_SECRET`, `AES_256_KEY`).
- **"Subscription ended"** for a customer → Payments → Record payment (or Customers → Edit → Paid until).
- **R2 not uploading** → System & Backups shows the last error; check the four `R2_…` values and the token's bucket permission.
